# Boundaries

Three-tier permission system for AI agent actions.

## Always Do

- Forks go to `{{shooter:paths.forks}}/<repo-name>/` — never `~/a/`; no shooter setup or beads init in forks
- Push after every commit (no local-only commits)
- Use beads (`bd create`, `bd close`) for task tracking
- Bump `.shooter/VERSION` patch before every commit
- Run configured pre-commit checks (format, lint, typecheck, build) before committing
- Quote all shell variables and use `set -euo pipefail`; use `printf` not `echo`
- Update `.shooter/ai/context.md` after corrections from the user
- Stage specific files, not `git add -A` or `git add .`
- After modifying any instruction file in `ai/instructions/`: run `shoc ai memory project ensure` to regenerate AGENTS.md, CLAUDE.md, GEMINI.md
- After creating/modifying any agent, command, skill, or rule: run `shoc ai util dist-to-clis` to ensure all 4 major CLIs (Claude, Gemini, OpenCode, Codex) have the latest artifacts
- Run `shoc ai util dist-verify` before any release to confirm cross-CLI parity
- Write all configuration files in YAML format (never JSON or TOML); sort YAML keys alphabetically
- One logical change per commit
- 80%+ test coverage for new code (unit tests)
- Never delete existing tests — only add or update
- Clean up test resources after runs (no orphan processes)

## Ask First

- Architectural changes (new directories, new patterns, new layers)
- Adding external dependencies
- Deleting files or directories
- Changing CI/CD configuration
- Modifying Human Notes section of `.shooter/ai/context.md` (human-owned)
- Bumping minor or major version (patch only for AI)
- Creating new instruction files or skills

## Never Do

- Modify linter, formatter, or type-checker configuration
- Force push to main/master
- Skip git hooks (`--no-verify`)
- Commit secrets, keys, tokens, or `.env` files
- Suppress lint/format/type warnings instead of fixing them
- Lower test coverage thresholds
- Use interactive git flags (`-i`)
- Edit autogenerated files (AGENTS.md, CLAUDE.md, GEMINI.md) directly
- Edit files in `.shooter/ai/codebase/` — they are autogenerated by `sho-codebase-mapper` agents
- Edit shotfiles (`.shooter/ai/shotfiles/`) — they are human-owned, read-only for AI
- Delete `.beads/` directory
- Skip tests (`.skip()`, `test.skip()`, `@Disabled`, etc.)
- Ignore build warnings — builds must be clean

## Script Quality Rules

Shell scripts must follow these standards:
- No silent failures: `2>/dev/null || true` only for non-critical operations (logging, metrics). Never for git, file mutations, or beads operations.
- Explicit error handling: check exit codes, log errors to stderr with context, exit with appropriate code (1=usage, 2=precondition, 3=data).
- Idempotency: same result when run multiple times. Use `skip:` prefix when already complete.
- Temp file cleanup: `trap 'rm -f "$tmp_file"' EXIT`

# Shooter Workflow Orchestration Pipeline

This is a shooter project. Follow this pipeline for every task. Output **`Step N/8: <name>`** before each step.

## Routing

| Classification | Path | Steps |
|---------------|------|-------|
| question | quick | 1 → answer directly |
| quick | quick | 1 → 5 → 8 |
| follow-up | quick | 1 → 5 → 8 |
| research | full | 1 → 2 → 3 → 8 |
| epic | full | 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8 |

## Beads Tracking

Beads are the persistent task tracker. Every piece of work gets a bead. Hierarchy: **Theme → Epic → Issues**.

- **Theme bead** (`--type=theme`): One per theme, permanent. Verify with `bd list --type=theme`.
- **Epic bead** (`--type=epic`, `--parent=<theme-id>`): One per plan or body of work.
- **Issue beads** (`--type=task|bug|feature`, `--parent=<epic-id>`): Individual work items.
- **Shots epic** (`<slug>-shots`): Permanent epic per theme for ad-hoc/quick work.

> **Troubleshooting**: If a `bd` command fails or you're unsure about flags, read `~/.config/shooter/_source/ai/references/beads.md`. If you solve a beads problem not covered there, append the solution to that file.

| Task type | When to create beads | What to create |
|-----------|---------------------|----------------|
| epic | Step 4 (Plan), before execution | Epic bead + issue beads with `plan:wave:N` labels |
| quick | Step 8 (Finalize), after completion | Single issue bead under theme's shots epic |
| research | Step 8 (Finalize), after completion | Single issue bead (if findings are significant) |

### Bead descriptions (MANDATORY — every bead, no exceptions)

**Every single bead MUST have a rich `--description`**, regardless of type or complexity. This applies equally to quick fixes, simple tasks, bug fixes, epics, and research. No bead is too small for a proper description.

Beads are the project's persistent memory — anyone reading a bead should understand the complete picture without looking elsewhere. A bead without a description is useless.

Always use markdown formatting and include at minimum:
- **What** was done (or planned)
- **Why** it was done
- **Which files** were changed (or will be changed)

Additional detail by bead type:
- **Epic beads**: Also include the full plan (waves, tasks, acceptance criteria, architectural decisions, rationale).
- **Issue beads under epics**: Also include acceptance criteria, approach, and deviations from the plan.
- **Quick/research beads**: Also include the original request and any decisions made.

### Creating quick/research beads (Step 8)

Quick and research tasks create their bead **after** the work is done, during Step 8 (Finalize). This is mandatory — every task gets a bead, not just epics.

```bash
# 1. Find the theme's shots epic
bd list --type=epic  # e.g. sho-abc = ai-shots
# 2. Create a single issue bead under it with a RICH description
bd create --type=task --parent=<shots-epic-id> --title="<what was done>" \
  --description="## What was requested
<original request summary>

## What was done
<detailed description of changes made>

## Files changed
- <file1>: <what changed and why>
- <file2>: <what changed and why>

## Decisions made
<any decisions or trade-offs, if applicable>"
bd close <new-id> --reason="<brief summary>"
bd sync
```

> **Do not skip this.** If you completed work and changed files, it gets a bead. The only exception for research tasks is when findings are trivial or inconclusive.

### Creating epic beads (Step 4)

```bash
# 1. Find theme bead
bd list --type=theme  # e.g. sho-abc = shooter/cli
# 2. Create epic under theme with the FULL PLAN as description
bd create --type=epic --parent=<theme-id> --title="Epic title" --priority=2 \
  --description="## Plan
<full plan content: goals, approach, architecture decisions>

## Waves

### Wave 1: <wave description>
- Task 1: <description>
- Task 2: <description>

### Wave 2: <wave description>
- Task 3: <description>

## Acceptance criteria
<overall epic acceptance criteria>

## Rationale
<why this approach was chosen, alternatives considered>"
bd update <epic-id> --set-labels "theme:<slug>"
# 3. Create issue beads per plan task with DETAILED descriptions
bd create --type=task --parent=<epic-id> --title="Task description" \
  --description="## Goal
<what this task accomplishes>

## Approach
<how to implement — specific files, functions, patterns>

## Acceptance criteria
- [ ] <criterion 1>
- [ ] <criterion 2>

## Files to change
- <file1>: <what to change>
- <file2>: <what to change>"
bd update <issue-id> --set-labels "theme:<slug>" --set-labels "plan:wave:1"
# 4. Add cross-wave dependencies
bd dep add <wave2-id> <wave1-id>
```

### During execution (Step 5)

```bash
bd update <id> --status=in_progress   # Before starting each task
```

### Updating beads during execution (Step 5)

When completing a task, update its description with what was actually done:

```bash
# After completing work on an issue, update with actual results
bd update <id> --description="## Goal
<original goal>

## What was done
<detailed description of actual implementation>

## Files changed
- <file1>: <what changed>
- <file2>: <what changed>

## Deviations from plan
<any changes from original approach, and why>

## Acceptance criteria
- [x] <criterion 1 — met>
- [x] <criterion 2 — met>"
```

### Closing beads (Step 8)

```bash
bd close <id1> <id2> ... --reason="What was done"
# Close epic after all children are closed — include summary of all work
bd close <epic-id> --reason="<comprehensive summary: what was accomplished, key decisions, files changed>"
bd sync
```

## Steps

### 1. Classify (always)
Determine task type: `question | quick | epic | research | follow-up`. Identify affected theme(s) or `_project`.

### 2. Research (if needed)
Parallel research: codebase, docs (context7), web. Collect open questions.

Also consult existing knowledge in the affected theme's `.shooter/ai/` folder:
- `historic-decisions.md` — prior architectural decisions (avoid re-deciding settled questions)
- `historic-learnings.md` — patterns and gotchas discovered in earlier sessions
- `historic-q-and-a.md` — questions already asked and answered

### 3. Discuss (if open questions exist)
Use AskUserQuestion for open questions. Skip if user said "auto" or "you decide".

### 4. Plan (epic or >3 steps)
- Write plan to `.shooter/ai/plans/<YYYYMMDD-HHMM>-<descriptive-plan-name>.yaml`
- Organize into waves (parallel within wave, sequential across waves)
- Wave rules: no shared file dependencies, no task dependencies within a wave
- Define acceptance criteria per task
- Show plan to user, offer discussion, iterate until accepted

### 5. Execute (always after planning or directly for quick tasks)
Execute wave-by-wave. Collect per-agent: errors, learnings, open questions.

### 6. Verify (after execution, when acceptance criteria exist)
- Check acceptance criteria from plan. If failing → loop back to step 5
- Verify builds pass, tests pass
- If open questions → loop back to step 3
- Offer user to create follow-up tasks via AskUserQuestion

### 7. Compound (after verify)
Persist artifacts from this work session. Write to the **affected theme's** `.shooter/ai/` folder (e.g. `cli/.shooter/ai/historic-decisions.md`). For cross-theme or project-level work, write to `.shooter/ai/` at the repo root.

**Prepend** new entries (newest first) to each file. Only persist entries that are genuinely useful for future sessions — skip trivial or one-off details.

#### 7a. Decisions → `historic-decisions.md`
Record architectural decisions, technology choices, or design trade-offs made during this session.

Entry template:
```
## <Title> (<YYYY-MM-DD HH:MM>)

**Theme:** <theme-slug>
**Decision:** <what was decided>
**Reason:** <why this was chosen over alternatives>
**Implementation:** <how it was implemented> (optional)
**Bead:** <bead-id> (optional)
```

#### 7b. Learnings → `historic-learnings.md`
Record patterns, gotchas, or reusable knowledge discovered during implementation.

Entry template:
```
## <Title> (<YYYY-MM-DD HH:MM>)

**Theme:** <theme-slug>
**Learning:** <what was learned>
**Context:** <what task/situation surfaced this>
**Pattern:** <reusable rule or pattern> (optional)
**See:** <file:line references> (optional)
```

#### 7c. Q&A → `historic-q-and-a.md`
Record questions asked during Step 3 (Discuss) and their answers, so future sessions don't re-ask the same questions.

Entry template:
```
## <Question> (<YYYY-MM-DD HH:MM>)

**Theme:** <theme-slug>
**Answer:** <detailed answer, including reasoning and alternatives considered>
```

#### 7d. Other artifacts
- Context updates → `.shooter/ai/context.md` (AI Learnings section)
- Research → `.shooter/ai/research/<topic-slug>.md`
- Plans → `.shooter/ai/plans/`

### 8. Finalize (always, last step)
- **Create bead** if this was a quick or research task (see "Creating quick/research beads" above)
- Commit with conventions (see commit conventions)
- Bump `.shooter/VERSION` patch
- Push to remote
- `bd sync` if beads were modified

## Session Close Checklist (MANDATORY)

Before declaring work complete, execute ALL of these in order:

1. `git status` — verify what changed
2. `git add <specific-files>` — stage code changes (never `git add .`)
3. Commit with conventions
4. **Create bead** — quick/research tasks: create + close a bead under the theme's shots epic (see "Creating quick/research beads")
5. Persist decisions → `historic-decisions.md` (if any decisions were made)
6. Persist learnings → `historic-learnings.md` (if any patterns/gotchas discovered)
7. Persist Q&A → `historic-q-and-a.md` (if any questions were discussed in Step 3)
8. `bd sync` — sync beads if modified
9. `git push` — push to remote

NEVER skip this checklist. Work is not done until pushed.

# Commit conventions

Git commit standards for all repositories.

## Format

```
type(scope): description (vX.Y.Z)

Optional body explaining WHY, not WHAT.

Beads: <bead-id-1>, <bead-id-2>
Co-Authored-By: <name> <email>
```

## Subject Line

- Use conventional commits: `type(scope): description (vX.Y.Z)`
- Keep under **60 characters** (including version)
- Use imperative mood: "add feature" not "added feature"
- Lowercase after the colon
- End with version in parentheses: `(v0.2.1)`

## Types

| Type       | When to use                        |
|------------|------------------------------------|
| `feat`     | New feature or capability          |
| `fix`      | Bug fix                            |
| `refactor` | Code change that doesn't fix/add   |
| `docs`     | Documentation only                 |
| `chore`    | Maintenance, deps, config          |
| `test`     | Adding or updating tests           |
| `ci`       | CI/CD pipeline changes             |
| `perf`     | Performance improvement            |
| `style`    | Formatting, whitespace, lint fixes |

## Trailers

- **Co-Authored-By** (required for AI commits): `Co-Authored-By: Claude Opus 4.5 <noreply@anthropic.com>`
- **Beads** (required when working on beads): `Beads: sho-abc.1, sho-abc.2`
- If the commit is not related to any bead, omit the Beads trailer

Example:
```
feat(auth): add JWT validation (v0.2.1)

Implement RS256 token validation with refresh support.

Beads: sho-abc.1
Co-Authored-By: Claude Opus 4.5 <noreply@anthropic.com>
```

## Version Bumping

Every commit bumps `.shooter/VERSION` (patch only for AI agents). Minor/major bumps are human-only via `aid-release`. `shoc ai util commit` handles version bumping automatically.

When bumping `.shooter/VERSION`, also update the version in the project's workspace manifest if one exists:
- **Rust (Cargo):** `workspace.package.version` in root `Cargo.toml`
- **Node (Turborepo/Nx):** `version` in root `package.json`
- **Python:** `version` in `pyproject.toml`

All version sources must stay in sync with `.shooter/VERSION`.

## Post-Push

After every `git push`, rebuild release binaries if the project uses a supported build system:
- **Rust (Cargo):** `cargo build --release`
- **Node:** `npm run build` or `pnpm build` (if build script exists)
- **Python:** `python -m build` (if `pyproject.toml` has a build backend)

## Release conventions

- **Never create releases** — releases are human decisions via `aid-release`
- Release commits: `chore(release): vX.Y.Z` — created by `aid-release`, never manually
- CHANGELOG.md is auto-maintained by `shoc ai util commit`
- Do not manually edit versioned changelog sections
- Do not create git tags — tags are created by `aid-release`
